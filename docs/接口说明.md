# REST API

本文对应当前 V1–V7 数据库迁移。医嘱接口不接受头级 `orderType`、`frequency` 或 `workflowVersion`；长期/临时属性位于每个医嘱项目，执行按 `DISPENSE`、`ADMINISTER`、`PERFORM` 三个环节处理。药品处方、计划任务和实际执行分别存放于 `order_item`、`medication_schedule`、`execution_record`。

所有接口以 `/api` 开头，请求使用 `Authorization: Bearer <JWT>`。

统一响应：

```json
{
  "code": "OK",
  "message": "操作成功",
  "data": {},
  "traceId": "32位追踪号",
  "timestamp": "UTC时间"
}
```

分页数据为 `{items,total,page,size}`。参数或业务状态错误通常返回 HTTP 400，数据库竞争/约束冲突返回 409，未认证返回 401，无权限返回 403，不存在返回 404。

## 当前关键行为（按现存源码核对）

- `POST /auth/password`：登录用户提交 `{oldPassword,newPassword}`；新密码至少10字符且UTF-8不超过72字节，修改后必须重新登录。
- `PUT /admin/users/{id}/enabled`：`{enabled:true|false}`；不能停用自己或最后一个有效管理员，变更后旧令牌失效。
- `GET /auth/me` 返回完整 `id,username,displayName,roles,permissions`；每次认证从数据库读取当前权限。
- `GET /admissions` 默认查询在院/待出院；`status=ALL` 包含历史；`keyword` 匹配患者姓名、患者号或住院号；支持 `page,size`，单页最多100条；可用 `departmentId`、`longStayDays`、`settlementBlocked` 筛选科室、长住院和结算受阻病例。
- `POST /admissions`：`{patientId,departmentId,doctorId,bedId,initialDeposit,paymentMethod}`；初始押金大于零时，支付方式会写入对应押金流水。
- `POST /admissions/{id}/transfer`：`{targetBedId,targetDoctorId,reason}`；同科医生可省略，跨科必须传目标科室医生，并先处理全部未完成医嘱。
- `POST /admissions/{id}/withdraw-discharge`：撤回待出院状态；结算后不能撤回。
- `POST /orders`：`{admissionId,note,items}`；药品项目使用 `medicalItemId,dosePerAdministration,requestedDispenseQuantity,doseUnit,route,orderType,administrationMode,administrationIntervalMinutes,maxAdministrationsPerDay,startTime,endTime` 中适用的字段；非药品项目使用 `executionQuantityPerOperation`。项目独立执行。
- 临时药品固定为 `TEMPORARY + ONCE`，提交后只生成一个给药任务；长期药品使用 `SCHEDULED` 或 `PRN`，按间隔滚动生成任务，PRN 还必须设置每日最大次数。停止、撤销或完成项目会取消尚未执行的任务。
- `GET /orders/tasks`：默认 `view=EXECUTABLE`，返回 `{items,total,page,size}`；支持 `keyword`（患者、住院号、床号、医嘱号或项目）、`administrationMode`、`timeliness=OVERDUE|DUE_30`、计划时间范围、`dispenseStatus=NOT_DISPENSED|INSUFFICIENT|READY`、科室和计划时间升降序。`view=FUTURE&windowHours=2|4|8` 仅用于护士给药排班预览，返回行带 `preview_only=true`，不能执行。
- `POST /orders/executions`：`{requestNo,orderItemId,scheduleId,phase,actualQuantity,quantityVarianceReason,notDone,note}`；`phase` 仅允许 `DISPENSE`、`ADMINISTER`、`PERFORM`。给药必须关联待执行的 `scheduleId`；实际数量偏离处方剂量或建议发药量时必须填写 `quantityVarianceReason`。`notDone=true` 必须填写原因，且不能用于发药；定时任务计划时间超过30分钟的迟发给药也必须填写原因。
- 药房或管理员负责 `DISPENSE`，护士或管理员负责 `ADMINISTER`；非药品 `PERFORM` 必须匹配目录项目的执行岗位。冲正权限沿用原环节。
- 新建药品的初始库存为零，之后通过库存入库增加；入库请求为 `{quantity,note}`，盘点请求为 `{actualQuantity,note}`，两者均在同一事务内更新余额和追加库存流水。库存调整为实际数量，不能用于直接修改历史流水。
- `PUT /inventory/{itemId}/threshold` 使用 `{threshold}`；传 `null` 表示关闭该药品的低库存预警。库存为零优先标记为缺货。
- `POST /deposits`：`{admissionId,type,amount,paymentMethod,note,requestNo}`；`requestNo` 必填且全局唯一。amount传正数（最多两位小数），退款由服务转负数；type 为 INITIAL/SUPPLEMENT/REFUND。
- `POST /settlements/{id}`：`{paymentMethod}`；存在结算退款时，该方式写入自动生成的退款流水。支付方式统一允许 `CASH`、`CARD`、`TRANSFER`。
- 临时药品成功给药一次即完成，不再保存“计划给药总次数”；长期药品每次成功或未执行后按规则生成下一任务。发药量与给药剂量分别使用库存单位和剂量单位，余额可通过 `v_order_item_medication_balance` 核对。重复请求会被拒绝，客户端应刷新核对，不能改号盲目重试。
- 定时给药超过计划时间30分钟为逻辑逾期，不会自动写成漏服。迟发成功后，系统跳过积压的历史计划点，并从“实际给药时间 + 处方间隔”之后选择第一个原常规时点；登记未执行后则选择当前时刻之后的第一个原常规时点。按需给药不适用逾期规则。
- 医生仅访问其主管住院；护士仅访问当前所属科室的住院，且不能发药。住院处、收费、药房、管理员按岗位权限访问跨科数据。混合角色中具有上述全院岗位时按全院范围处理。
- 已结算住院只读：不能执行、转床、改押金、冲正、撤回或重复结算。待出院需撤回才能继续诊疗。
- 业务状态错误通常为 400，数据库竞争/约束冲突为 409；401/403/404 分别表示会话失效、越权、不存在。响应包含追踪号，数据库结构和原始 SQL 错误不直接回传客户端。
