# REST API

本文对应当前 V1–V5 重建基线。医嘱接口不接受头级 `orderType`、`frequency` 或 `workflowVersion`；长期/临时属性位于每个医嘱项目，执行按 `DISPENSE`、`ADMINISTER`、`PERFORM` 三个环节处理。

所有接口以 `/api` 开头，请求使用 `Authorization: Bearer <JWT>`。

统一响应：

```json
{
  "code": "OK",
  "message": "操作成功",
  "data": {},
  "traceId": "32位追踪号",
  "timestamp": "UTC时间"
}
```

分页数据为 `{items,total,page,size}`。业务冲突通常返回 HTTP 400，未认证返回 401，无权限返回 403，不存在返回 404。

## 当前关键行为（2026-08-29）

- `POST /auth/password`：登录用户提交 `{oldPassword,newPassword}`；新密码至少10字符且UTF-8不超过72字节，修改后必须重新登录。
- `PUT /admin/users/{id}/enabled`：`{enabled:true|false}`；不能停用自己或最后一个有效管理员，变更后旧令牌失效。
- `GET /auth/me` 返回完整 `id,username,displayName,roles,permissions`；每次认证从数据库读取当前权限。
- `GET /admissions` 默认查询在院/待出院；`status=ALL` 包含历史；`keyword` 匹配患者姓名、患者号或住院号；支持 `page,size`，单页最多100条。
- `POST /admissions/{id}/transfer`：`{targetBedId,targetDoctorId,reason}`；同科医生可省略，跨科必须传目标科室医生，并先处理全部未完成医嘱。
- `POST /admissions/{id}/withdraw-discharge`：撤回待出院状态；结算后不能撤回。
- `POST /orders`：`{admissionId,note,items}`；每个项目包含 `medicalItemId,quantity,dosage,doseUnit,route,orderType,startTime,endTime,groupKey,plannedAdministrationCount,excessDispenseReason` 中适用的字段。
- `POST /orders/executions`：`{requestNo,orderItemId,phase,notDone,note}`；`phase` 仅允许 `DISPENSE`、`ADMINISTER`、`PERFORM`。`notDone=true` 必须填写原因，且不能用于发药。
- 药房或管理员负责 `DISPENSE`，护士或管理员负责 `ADMINISTER`；非药品 `PERFORM` 必须匹配目录项目的执行岗位。冲正权限沿用原环节。
- `POST /deposits`：`{admissionId,type,amount,paymentMethod,note,requestNo}`；`requestNo` 必填且全局唯一。amount传正数（最多两位小数），退款由服务转负数；type 为 INITIAL/SUPPLEMENT/REFUND。
- 临时药品发药一次后不能重复发药，给药达到 `plannedAdministrationCount` 才完成；其他临时项目成功执行一次即完成。重复请求会被拒绝，客户端应刷新核对，不能改号盲目重试。
- 医生仅访问其主管住院；护士仅访问当前所属科室的住院，且不能发药。住院处、收费、药房、管理员按岗位权限访问跨科数据。混合角色中具有上述全院岗位时按全院范围处理。
- 已结算住院只读：不能执行、转床、改押金、冲正、撤回或重复结算。待出院需撤回才能继续诊疗。
- 业务状态错误通常为 400，数据库竞争/约束冲突为 409；401/403/404 分别表示会话失效、越权、不存在。响应包含追踪号，数据库结构和原始 SQL 错误不直接回传客户端。
